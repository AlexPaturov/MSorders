# Блок B. Данные: PostgreSQL, конкурентность, пагинация

План действий для блока B из `plan-level-2.4.md`. Документ фиксирует проблему, что нужно понять, контракты и шаги, которые закрывают критерий блока.

## Проблематика

1. `GET /orders/all` читает и отдаёт все заказы владельца: ответ растёт вместе с объёмом данных и не имеет предсказуемой границы.
2. Два клиента могут обновить один заказ на основе устаревших данных; последний запрос молча перезапишет результат первого.
3. Batch-обновление проверяет наличие id до изменения, но между чтением и сохранением данные могут измениться; без версии и явной транзакции результат параллельных запросов непредсказуем.
4. Сортировка без подходящего индекса заставит базу сканировать строки владельца и сортировать их на каждый запрос списка.

### Как делаем проблему 1 видимой

Согласованы два шага:

- [ ] 1. Измерить текущее поведение `GET /orders/all`: засеять одному владельцу произвольное количество заказов через параметр `count`, записать в этот раздел количество записей в ответе и размер ответа. Значения `0`, `100`, `100 000` и больше одинаково возможны; локальный замер берёт небольшое значение, не объявляя его эталоном.
- [ ] 2. Добавить параметризованный тест-демонстратор: он сеет выбранное `count`, печатает количество записей и размер ответа, а после внедрения пагинации проверяет `pageSize` и границы страницы. Точное общее число заказов не используется как критерий корректности теста.

## Что мы должны понять

1. Чем unbounded-ответ отличается от страничного и почему `totalCount` нужен клиенту для навигации.
2. Почему проверки «заказ есть/нет» недостаточно для конкурентности: она не защищает от lost update.
3. Чем оптимистичная конкурентность отличается от пессимистичной и почему конфликт версии должен быть `409 Conflict`.
4. Почему batch-обновление должно быть одной транзакцией, а не просто проверкой перед `SaveChangesAsync`.
5. Почему стабильная сортировка и составной индекс `(OwnerId, Created, Id)` нужны именно вместе.

## Цель блока

Список заказов отдаётся страницами, а параллельное изменение одного заказа заканчивается предсказуемым `409 Conflict`, а не тихой перезаписью. Batch-обновление остаётся атомарным и при конкурентных запросах.


## Как это будет работать

1. Список перестаёт быть unbounded: `GET /orders` применяет фильтр владельца, необязательный фильтр `status`, стабильную сортировку и `Skip`/`Take`, а `totalCount` даёт клиенту число страниц.
2. Стабильная сортировка `Created DESC, Id DESC` исключает повторение или пропуск строк между страницами.
3. Версия заказа фиксирует состояние, на которое опирался клиент. Устаревшая версия в обновлении отклоняется с `409`, вместо того чтобы перезаписать более свежие данные.
4. Batch-обновление читает, проверяет, изменяет и сохраняет строки в одной транзакции: конфликт в любом элементе откатывает весь запрос.
5. Составной индекс `(OwnerId, Created, Id)` делает страничную выборку предсказуемой по стоимости, а не полным сканированием заказов владельца.

## Контракт пагинации

### Запрос

```text
GET /orders?page=1&pageSize=20&status=Processing
```

1. `page` — номер страницы с `1`; значение меньше `1` отклоняется как `400`.
2. `pageSize` — размер страницы; допустимый диапазон `1..100`, по умолчанию `20`.
3. `status` — необязательный фильтр по статусу; пустая строка обрабатывается как «без фильтра».
4. `sort` в блок не входит: порядок фиксирован как `Created DESC, Id DESC`.

### Ответ

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "totalCount": 0
}
```

1. `totalCount` считается после фильтрации по владельцу и `status`, до `Skip`/`Take`.
2. `items` содержит `OrderDto`, включая `Version`.
3. `OwnerId` в ответ не попадает.

## Контракт конкурентности

1. `Order.Version` — `Guid`, настройка в `OrdersDbContext`: `IsConcurrencyToken()`, `HasDefaultValueSql("gen_random_uuid()")`, `ValueGeneratedOnAdd()`.
2. `OrderDto.Version` отдаёт текущую версию клиенту.
3. `BatchUpdateOrderDto` получает поле `Version`; обновление без версии или с `Guid.Empty` отклоняется как `400`.
4. При успешном обновлении сервер генерирует новую версию каждого заказа.
5. `DbUpdateConcurrencyException` превращается в `409 Conflict` с текстом `"The order was modified by another request."`.
6. `403` и `404` сохраняют смысл из блока A: права и отсутствие заказа у текущего пользователя. Конфликт версий — отдельный `409`.

## Критерий готовности

1. Проблема unbounded-списка решена: `GET /orders` возвращает страницу с ограниченным `pageSize`, корректным `totalCount` и не показывает чужие заказы.
2. Проблема тихой перезаписи решена: устаревшая версия даёт `409 Conflict`, а данные остаются в состоянии, которое успешно записал первый запрос.
3. Проблема частичного batch решена: конфликт в любом элементе откатывает весь запрос, а не меняет часть заказов.
4. Мы можем объяснить выбор явной версии `Guid`, стабильной сортировки и составного индекса, а также почему `409` — правильный ответ на конфликт.
5. Тесты зелёные локально и покрывают три отказа выше: страничный список, конфликт одного заказа и конфликт batch.
