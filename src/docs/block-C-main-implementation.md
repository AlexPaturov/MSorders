# Блок C. Основное: план реализации

## Задание

Сценарий глазами клиента:

1. В системе есть клиенты. У каждого клиента постоянный идентификатор.
2. Клиент оформляет заказ, и заказ записывается на его идентификатор.
3. Клиент запрашивает свои заказы и видит только их.
4. Когда сервис клиентов недоступен, оформление заказа отвечает понятной ошибкой.

Поля клиента: `id` и `name`. Это минимум, который нужен сценарию: `id` связывает заказ с клиентом, `name` помогает различать клиентов в тестовых данных. Состав полей можно менять по ходу работы, ничто в плане не привязано к другим полям.

### Тестовые клиенты

| Имя | CustomerId | Заказы |
| --- | --- | --- |
| Alice | `11111111-1111-1111-1111-111111111111` | 3 |
| Bob | `22222222-2222-2222-2222-222222222222` | 1 |
| Carol | `33333333-3333-3333-3333-333333333333` | 0 |

Идентификаторы составлены по шаблону, поэтому читаются в логах, ответах и запросах с первого взгляда. Для 4-го и 5-го клиента подойдут `4444…` и `5555…` по тому же шаблону. Carol без заказов нужна для проверки: её список заказов пуст, значит заказы Alice и Bob ей не попадают.

### Откуда берутся идентификаторы

- В реальной системе идентификатор клиента выдаёт провайдер аутентификации (Google и подобные). После входа провайдер сообщает, кто пользователь, и идентификатор остаётся одним и тем же при каждом входе. Сервис получает его из токена.
- В учебной системе роль провайдера играют тестовые клиенты из таблицы. Их идентификаторы фиксированы и записаны в этой таблице, в сервисе `Customers` (шаг 2) и в коллекции запросов (ниже).
- В блоке A заглушка-издатель токенов выдаёт токены для тех же Alice, Bob и Carol с теми же идентификаторами. Тогда `Orders` берёт `CustomerId` из токена вместо параметра запроса, а тестовые клиенты из этого блока остаются прежними.

### Как это выглядит в работе

Коллекция запросов в Postman. В окружении три переменные (`alice`, `bob`, `carol`), в каждой идентификатор из таблицы. Запросы используют переменные, а идентификаторы в URL и теле не набираются вручную:

- `GET /customers`: список всех клиентов с их `id`
- коллекция «Тестовые данные»: создаёт 3 заказа для `{{alice}}` и 1 заказ для `{{bob}}`, запускается одной кнопкой (Collection Runner)
- `GET /orders?customerId={{alice}}`: 3 заказа
- `GET /orders?customerId={{bob}}`: 1 заказ
- `GET /orders?customerId={{carol}}`: пустой список

## Результат

К концу блока есть два сервиса, `Orders` и `Customers`. Каждый имеет свой проект, свою сборку, свой контейнер и свои данные. `Orders` обращается к `Customers` по HTTP через контракт и отвечает понятной ошибкой, когда `Customers` недоступен.

## Что опирается на предыдущие этапы

- Этап 5: конфигурация и Options pattern. Адрес `Customers` приходит из конфигурации.
- Этап 6: `ProblemDetails` и глобальный обработчик исключений. Ошибки соседа превращаются в аккуратный ответ.
- Этап 7: логи с шаблонами сообщений и `/health`.
- Этап 8: Swagger как контракт. Контракт `Customers` описывается там же.
- Этап 9: Docker и compose. Второй сервис добавляется в существующий compose-файл.

## Шаг 0. Структура репозитория

Рекомендация: один репозиторий, в нём папка на каждый сервис. У каждого сервиса свой `.csproj`, свой `Dockerfile` и свой набор тестов. Каждый сервис лежит в своём солюшене (`.sln`), проекты одного сервиса не ссылаются на проекты другого. Независимость сервиса определяется тем, что он собирается и запускается сам по себе, в каком бы репозитории он ни лежал. Когда дойдёшь до блока F, у каждого сервиса будет собственный шаг сборки.

Задача: перенеси `Orders` в папку сервиса и подготовь рядом место для `Customers`. Убедись, что `Orders` по-прежнему собирается и запускается через compose.

## Шаг 1. Контракт `Customers` до кода

Сначала фиксируем договорённость, потом пишем реализацию.

Что принадлежит `Customers`: клиенты и их данные. Что нужно от него `Orders`: подтвердить, что клиент существует, и (по желанию) узнать его имя.

Задача: опиши контракт в виде таблицы:

- `POST /customers`: создание клиента, ответ `201` с `id`
- `GET /customers/{id}`: `200` с `{ id, name }` или `404`
- `GET /customers`: список клиентов с их `id`
- формат ошибок: `ProblemDetails`, как в `Orders`

Реши и запиши:

- Тип идентификатора. Рекомендация: `Guid`, как и у заказов, тогда идентификаторы выглядят одинаково в обоих сервисах.
- Что `Orders` хранит о клиенте. Рекомендация: только `CustomerId`. Имя клиента остаётся данными `Customers`, и `Orders` запрашивает его через API, когда оно нужно.

## Шаг 2. Проект `Customers`

Задача: создай второй Web API проект с контроллерами (как у `Orders`).

- Модель `Customer` с минимальным набором полей (id, имя)
- Свой `DbContext`, своя миграция, свой файл базы SQLite
- Эндпоинты из контракта: создание, получение по id, список
- Тестовые клиенты из раздела «Задание»: при запуске в среде `Development` сервис добавляет их с фиксированными id, если их ещё нет. Повторный запуск оставляет ровно тех же клиентов. Рекомендация: так тестовые данные остаются вне миграций и в других средах появляться не будут.
- Отдельные DTO на вход и на выход, валидация, `ProblemDetails`, `/health`: всё по образцу `Orders`

Здесь повторяются шаги, которые ты уже прошёл для `Orders`, поэтому они пойдут быстрее. Если на каком-то шаге хочется скопировать из `Orders`, сначала реши, что действительно общее, а что принадлежит именно этому сервису (общий код между сервисами порождает связность, поэтому каждый сервис остаётся самостоятельным проектом).

Проверка: запусти `Customers` отдельно, создай клиента, получи его по id.

## Шаг 3. `Customers` в compose

Задача: добавь `Customers` в compose-файл рядом с `Orders`.

- Отдельный образ, отдельный контейнер, отдельный том для базы `Customers`
- Внутри контейнеров оба сервиса слушают один и тот же порт (по умолчанию .NET 8 это 8080), это нормально, потому что каждый в своём контейнере
- Наружу на хост пробрасываются разные порты, чтобы открыть Swagger каждого сервиса

Разберись: внутри сети compose сервисы находят друг друга по имени сервиса из compose-файла. Значит, адрес `Customers` для `Orders` строится из этого имени и внутреннего порта.

Проверка: `docker compose up` поднимает оба сервиса, Swagger каждого открывается на своём порту.

## Шаг 4. Адрес `Customers` в конфигурации `Orders`

Задача: добавь в `Orders` настройки обращения к `Customers` (базовый адрес и таймаут) через Options pattern. Значения в compose передаются переменными окружения, вложенный ключ записывается так, как ты уже разбирал на Этапе 9.

Реши: где лежит значение по умолчанию для локального запуска без Docker и где значение для compose.

## Шаг 5. Клиент к `Customers` в `Orders`

Задача: создай отдельный класс-клиент, который знает, как обращаться к `Customers`, и регистрируется через `IHttpClientFactory` (типизированный клиент).

- Прочитай в документации Microsoft, зачем для этого нужна фабрика и что происходит при создании `HttpClient` вручную на каждый запрос (проблемы с сокетами и обновлением DNS).
- Базовый адрес берётся из настроек шага 4.

Рекомендация по возвращаемым результатам метода «получить клиента по id», три исхода:

1. Клиент найден: возвращается его данные.
2. Клиент не найден (`404` от соседа): возвращается пустой результат. Это ожидаемая ситуация, как «не нашли заказ по id» на Этапе 3.
3. Сосед недоступен или ответил ошибкой сервера: клиент выбрасывает собственное исключение (например, `CustomersUnavailableException`), которое обрабатывается в шаге 7.

Всё знание о том, как устроен API `Customers`, живёт только в этом классе. Остальной код `Orders` работает с его методами. Классы для ответа `Customers` объявляются внутри `Orders` и содержат только те поля, которые `Orders` использует. Источник формата — контракт из шага 1 и Swagger сервиса `Customers`.

## Шаг 6. Таймаут

Задача: задай таймаут для клиента из настроек шага 4.

Разберись:

- Какой таймаут у `HttpClient` по умолчанию и почему это много для запроса, на который ждёт пользователь.
- Какое значение выбрать для локального учебного сервиса. Рекомендация: 2–3 секунды.

Таймаут и недоступность соседа обрабатываются одинаково: оба превращаются в `CustomersUnavailableException` из шага 5.

## Шаг 7. Использование клиента при создании заказа

Задача: в `Orders` добавь `CustomerId` в модель заказа, DTO создания и DTO чтения, создай миграцию.

При создании заказа (`POST /orders`):

1. Сервис вызывает клиент и проверяет существование клиента.
2. Клиент найден: заказ создаётся как раньше.
3. Клиент не найден: ответ `400` с `ProblemDetails` («клиент не найден»), заказ не создаётся. Рекомендация `400`: запрос ссылается на несуществующую сущность, это ошибка во входных данных.
4. Сосед недоступен: исключение попадает в глобальный обработчик.

В базе `Orders` `CustomerId` хранится обычным полем. Связь с клиентом проверяется вызовом API, а таблицы клиентов находятся в базе `Customers` и принадлежат только ему.

`GET /orders` принимает необязательный параметр `customerId` и возвращает заказы этого клиента. Заказ при создании записывается на `CustomerId` из запроса. Это основа сценария из раздела «Задание». Ограничение доступа по токену (клиент видит только свои заказы) появляется в блоке A.

Отдельно подумай и запиши решение: что делает batch-обновление заказов. Рекомендация: оно не обращается к `Customers`, пока `CustomerId` не меняется.

## Шаг 8. Ошибка недоступности в ответе

Задача: добавь в глобальный обработчик (Этап 6) обработку `CustomersUnavailableException`.

- Статус `503` и `ProblemDetails` с понятным заголовком («сервис клиентов временно недоступен»). Рекомендация `503` для обоих случаев (недоступен и таймаут): для клиента `Orders` суть одна, сервис не смог ответить сейчас.
- В логах одна запись уровня `Warning` с шаблоном сообщения и `CustomerId` в параметрах. Стек-трейс в ответ клиенту не попадает.
- Добавь `503` в описание ответов метода создания заказа в Swagger (Этап 8).

Проверка readiness: `/health` в `Orders` проверяет собственные зависимости (свою базу). Состояние `Customers` в нём не участвует: иначе при падении соседа `Orders` объявит себя недоступным и перестанет отвечать даже на запросы, которым клиенты не нужны.

## Шаг 9. Проверки руками

Выполни проверки блока и запиши результат каждой.

1. **Отказ соседа.** Останови `Customers` (`docker compose stop customers`). Создай заказ: ответ `503` с понятным `ProblemDetails`, быстро. Получение списка заказов и `/health` в `Orders` продолжают работать. Запусти `Customers` обратно: создание заказов снова проходит без перезапуска `Orders`.
2. **Зависший сосед.** Заморозь `Customers` (`docker compose pause customers`): порт открыт, ответа нет. Создание заказа завершается ответом `503` за время таймаута. Сними паузу.
3. **Независимый выпуск.** Измени что-нибудь в `Customers` (например, поле в ответе), пересобери только его (`docker compose up -d --build customers`). Контейнер `Orders` продолжает работать с прежним временем запуска.
4. **Граница данных.** Найди в коде `Orders` все места, где используются данные клиентов: это только класс-клиент из шага 5. Проверь, что том с базой `Customers` подключён только к контейнеру `customers`.
5. **Заказы клиентов.** Запусти коллекцию «Тестовые данные». Запросы со списками дают: Alice 3 заказа, Bob 1 заказ, Carol пустой список.

## Критерий закрытия

- Два проекта, два контейнера, один compose-файл, у каждого сервиса свои данные
- Контракт `Customers` описан и реализован, ошибки в формате `ProblemDetails`
- `Orders` обращается к `Customers` через типизированный клиент с таймаутом, адрес берётся из конфигурации
- Создание заказа проверяет клиента: `201`, `400` или `503`
- Остановка и заморозка `Customers` дают `503` быстро, остальные эндпоинты `Orders` работают
- Выпуск `Customers` происходит отдельно от `Orders`
- Тесты клиента и создания заказа проходят
- Тестовые клиенты добавляются при запуске, коллекция запросов даёт Alice 3 заказа, Bob 1, Carol 0
- Понятны ответы на 5 контрольных вопросов
