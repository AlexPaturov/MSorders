# Разбор проекта: «что сломано и исправить»

Рабочий документ для микросервиса **Orders**. Описывает алгоритм, по которому идём, и реестр находок, который наполняем по ходу.

## Правила игры

1. Сначала разведка и baseline, потом выводы. Никаких правок до того, как понято текущее поведение.
2. Read-only по умолчанию. Правка — только по явному запросу.
3. Одно изменение за раз; после каждого — проверка.
4. Каждая находка подкреплена доказательством: `файл:строка` и воспроизводимый шаг.
5. Различаем **сломано** (нарушено ожидаемое поведение) и **можно улучшить** (стиль, рефакторинг). Второе в рамки «исправь что сломано» не входит по умолчанию и выносится отдельным списком.
6. Документация — вторичный источник, код и поведение — первичный. Расхождение кода с docs — это сама по себе находка.
7. Не затирать незакоммиченную работу: перед правкой — `git status` / `git diff`.

## Фаза 0. Вход и критерии приёмки

1. Понять, что означает «работает» именно для этого проекта: назначение, границы, ожидаемое поведение.
2. Источники: `docs/` (план обучения и этапы), история git.
3. Выход фазы: критерии приёмки, сформулированные своими словами, — с чем будем сравнивать факт.

## Фаза 1. Разведка репозитория (read-only)

1. `git status` / `git log` / ветки — незакоммиченное, вложенные репозитории, история.
2. Структура каталогов и `.csproj` — тип проекта, зависимости, target framework.
3. Точка входа `Program.cs` — как собирается приложение и что в нём регистрируется.
4. Модель и persistence — сущности, `DbContext`, миграции, строка подключения.
5. Конфигурация и окружения — `appsettings*`, secrets, порядок переопределения.
6. Внешняя поверхность — контроллеры, маршруты, контракты.
7. Выход фазы: **карта проекта** (см. ниже).

## Фаза 2. Baseline: собрать и запустить

1. `dotnet restore` / `dotnet build` — зафиксировать ошибки и предупреждения компилятора.
2. Запуск в Development — поднимается ли сервис, доступен ли Swagger.
3. Smoke-тест CRUD: create → list → get → update → delete → get.
4. Перезапуск между шагами — переживают ли данные рестарт.
5. Выход фазы: зафиксированное «как ведёт себя сейчас» + воспроизводимые сценарии.
6. Примечание: сборку и запуск выполняем только после отдельной явной санкции.

## Фаза 3. Инвентаризация отклонений

Проходим по слоям и фиксируем всё, что расходится с ожиданием:

1. Компилятор: предупреждения (nullable, неиспользуемые члены), ошибки.
2. Конфигурация против запуска: обязательные поля, пустые значения, `ValidateOnStart`, активный провайдер.
3. Контракт API: маршруты, HTTP-глаголы, коды ответов, тела запросов/ответов.
4. Код против `docs/`: расхождения с зафиксированными решениями этапов.
5. Данные: миграции против фактического состояния БД.
6. Верность хранилища: двойные запросы, change tracking, `SaveChanges`.
7. Секреты и окружение: где фактически лежит строка подключения.
8. Гигиена репозитория: артефакты, вложенные `.git`, покрытие `.gitignore`.
9. Для каждой находки: что не так, доказательство, шаг воспроизведения, ожидание против факта.

## Фаза 4. Триаж и приоритет

Классифицируем по влиянию:

1. **Блокер** — не собирается, не стартует, основной сценарий не работает.
2. **Корректность** — работает, но результат неверный (данные, коды ответов).
3. **Контракт** — рассинхрон с документацией, решением или клиентом.
4. **Качество/гигиена** — стиль, предупреждения, состояние репозитория.

Порядок работы: 1 → 2 → 3 → 4. Категории 1–3 попадают под «исправь что сломано»; категория 4 согласуется отдельно.

## Фаза 5. Исправление

1. Один минимальный корректный фикс за раз.
2. Фикс в причине, а не заплатка на симптом.
3. После каждого фикса — повтор проверки из Фазы 2 для затронутого сценария.
4. Несвязанные улучшения — в отдельный список, не в тот же коммит.

## Фаза 6. Верификация и отчёт

1. Повторить smoke-сценарии целиком.
2. Отчёт: что нашли (с доказательствами), что починили, чем подтвердили, что осталось и почему.

## Критерии приёмки (выход Фазы 0)

«Работает» = для каждого сценария ниже факт совпадает с ожидаемым кодом и телом ответа.

### Сквозные инварианты

1. Персистентность: успешная запись видна в последующих чтениях и переживает перезапуск процесса.
2. Согласованность: содержимое БД совпадает с отдаваемым на чтении; `Id` и `Created` управляются сервером.
3. Единый формат ошибки RFC 7807 (ProblemDetails) для кодов 400 и 500.
4. Клиент получает аккуратный 500 и заголовки/тело без внутренностей стека.
5. Идемпотентность: `GET` и `DELETE` идемпотентны, `POST` создаёт запись.
6. Целостность: список отражает все успешные записи.

### Матрица по эндпоинтам

| Эндпоинт | Сценарий | Ожидание |
|----------|----------|----------|
| `POST /orders` | валидный ввод | 201, тело — созданный объект (серверные `Id`, `Created`), заголовок `Location` |
| `POST /orders` | невалидный ввод | 400 (ProblemDetails) |
| `GET /orders/all` | есть записи | 200, массив объектов |
| `GET /orders/all` | пусто | 200, пустой массив `[]` |
| `GET /orders/by-id/{id}` | существует | 200, объект |
| `GET /orders/by-id/{id}` | нет ресурса | 404 |
| `GET /orders/by-id/{id}` | id не приводится к Guid | 400 |
| `PATCH /orders` | валидный непустой список | 200, отчёт о применении |
| `PATCH /orders` | пустой список | 400 |
| `PATCH /orders` | невалидный элемент | 400 |
| `PATCH /orders` | хотя бы один id не найден | 404, атомарно: откат всей операции |
| `DELETE /orders/{id}` | существует | 204 |
| `DELETE /orders/{id}` | нет ресурса | 404 |
| `DELETE /orders/{id}` | повторное удаление | 404 (идемпотентно по результату) |

### Журнал решений Фазы 0

1. Update реализуется единым батч-эндпоинтом `PATCH /orders` (список, `Id` внутри каждого элемента) — по решению `docs/Этап_6_4.md`.
2. Батч-обновление атомарно: при первом ненайденном id клиент получает 404, применяется откат всей операции.
3. Удаление адресуется `DELETE /orders/{id}`, тело запроса пустое.
4. Уникальный бизнес-ключ у `Order` не задан (модель: `Id`, `Name`, `Status`, `Created`); проверяемые коды — 400/404/500.
5. `GET /orders/all` при пустом списке возвращает 200 с `[]`.
6. Успешный `PATCH /orders` возвращает 200 и массив обновлённых `OrderDto`.
7. Атомарность батча обеспечивает хранилище (`SqlVault.UpdateBatch`): загрузка всех сущностей одним запросом, при пропуске — `null` без `SaveChanges`, иначе один `SaveChanges` (одна транзакция).

## Карта проекта (по факту)

Проверенные факты текущего состояния:

1. Решение `Orders.sln`: два проекта — `src/Orders.csproj` (ASP.NET Core Web API, `net8.0`, `Nullable` и `ImplicitUsings` включены) и `tests/Orders.Tests/Orders.Tests.csproj`.
2. Пакеты (`src`): `Microsoft.EntityFrameworkCore.Sqlite` 8.0.31, `Microsoft.EntityFrameworkCore.Design` 8.0.31, `Swashbuckle.AspNetCore` 6.6.2.
3. Точка входа `src/Program.cs`: `AddControllers`, `AddSwaggerGen`, `AddDatabase`, регистрация `IVault → SqlVault`; обработка ошибок — `AddProblemDetails`, `AddExceptionHandler<GlobalExceptionHandler>`, `UseExceptionHandler`; Swagger включается в ветке Development; `public partial class Program` открывает тип для тестов.
4. Persistence: `src/Infrastructure/SqlDbContext.cs` с `DbSet<Order>`; миграция `20261003135127_Initial` создаёт таблицу `Orders` (`Id`, `Name`, `Status`, `Created`), миграция `20261018063003_AddedOrderCreatedDefault` задаёт для `Created` дефолт `CURRENT_TIMESTAMP`.
5. Хранилище: интерфейс `src/Repositories/Interfaces/IVault.cs` (namespace `Orders.Repositories.Interfaces`) и реализация `src/Repositories/Implementations/SqlVault.cs` (`Orders.Repositories.Implementations`), методы синхронные.
6. API: `src/Controllers/OrdersController.cs` — `GET /orders/all`, `GET /orders/by-id/{id}`, `PATCH /orders` (батч-обновление), `DELETE /orders/{id}`, `POST /orders` (201 + тело + `Location`).
7. Модель `src/Models/Order.cs`: `Id`, `Name`, `Status`, `Created`.
8. DTO: `src/DTOs/Orders/*` (namespace `Orders.DTOs`, атрибуты `[Required]`/`[MaxLength]` на входных полях) и маппер `src/DTOs/Mappers/OrderMappings.cs` (namespace `Orders.DTOs.Mappers`): `ToDto`/`ToDtos` (сущность → DTO), `ToEntity(CreateOrderDto)`/`ToEntity(BatchUpdateOrderDto)` (вход → сущность), expression-tree проекция.
9. Конфигурация: секция `Databases` (Sqlite, Postgres) и `DatabasesOptions` с полем `ActiveDatabase` и `ValidateOnStart`; в `src/Orders.csproj` задан `UserSecretsId`.
10. Тесты: `tests/Orders.Tests/` — reflection-тесты маппинга `Order → OrderDto`; интеграционные тесты API (`Api/`) на `WebApplicationFactory<Program>`: `OrdersEndpointsTests` (400/404/201/204, атомарность батча) и `ErrorHandlingTests` (500 через подменённый `IVault`).
11. Документы: в `src/docs/` — план обучения, `Этап_4`, `Этап_5`, `Этап_6`, `Этап_6_4`, этот файл.
12. Обработка ошибок: 400 — валидация + пустой batch; 404 — отсутствие ресурса; 500 — `GlobalExceptionHandler` (`IExceptionHandler`), клиент получает `ProblemDetails` без стека. 409 не применяется (нет уникального ключа).
13. Состояние репозитория: `app.db` вне контроля git; реструктуризация (`src/`, `tests/`, solution), миграции, мапперы, Шаги 2–6 и тесты — в репозитории.
