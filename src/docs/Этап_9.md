# Этап 9. Docker

## Зачем этот этап

Микросервис почти по определению живёт в контейнере: один образ, одинаково запускается на твоей машине, на сервере и в CI. Цель этапа: собрать образ сервиса, запустить контейнер, подключить к нему хранилище данных и убедиться, что всё, что ты настроил на Этапах 5–8 (конфигурация, логи, health checks), работает внутри контейнера.

Здесь же закрывается вопрос, который мы обсуждали на Этапе 5: переменные окружения как основной механизм конфигурации уместны именно тут, потому что каждый контейнер изолирован и конфликтовать с соседними проектами не может.

## Шаг 0. Проверка окружения

Задача: убедись, что Docker установлен и работает (`docker --version`, `docker run hello-world`). Пойми три базовых понятия, без них дальше будет путаница:

- **Образ (image)** — шаблон, собранный из инструкций
- **Контейнер** — запущенный экземпляр образа
- **Том (volume)** — хранилище, которое живёт отдельно от контейнера

## Шаг 1. Dockerfile: многостадийная сборка

Задача: напиши `Dockerfile` для сервиса. В .NET принято собирать образ в несколько стадий: одна стадия компилирует проект, другая содержит только то, что нужно для запуска.

Разберись сам:

- Чем отличается образ с `sdk` от образа с `aspnet` и почему финальный образ не должен включать SDK
- Какие теги базовых образов соответствуют .NET 8
- Как копировать файлы так, чтобы Docker переиспользовал кэш слоёв и не восстанавливал пакеты при каждой правке кода (порядок инструкций здесь важен, найди почему)

## Шаг 2. .dockerignore

Задача: создай `.dockerignore` и реши, что в образ попадать не должно. Подумай как минимум про `bin`, `obj`, `.git`, локальные файлы базы данных и всё, что содержит секреты. Вопрос для самопроверки: что произойдёт с размером образа и скоростью сборки без этого файла?

## Шаг 3. Порт и пользователь

Задача: в .NET 8 контейнеры ведут себя не так, как в .NET 7. Найди в документации Microsoft про изменения для контейнеров в .NET 8 и ответь:

- На каком порту по умолчанию слушает сервис в контейнере
- Под каким пользователем он запускается и почему это важно для прав на запись в файловую систему (пригодится в шаге 5)

Собери образ, запусти контейнер с пробросом порта и открой Swagger в браузере. Учти: Swagger у тебя включён только в `Development`, так что вспомни Этап 8 и реши, как запустить контейнер в нужном режиме.

## Шаг 4. Конфигурация через переменные окружения

Задача: передай контейнеру настройки так, как это принято: через переменные окружения при запуске, а не вшивая их в образ. Разберись:

- Как в переменной окружения записывается вложенный ключ конфигурации (подсказка: в `appsettings.json` это секция с вложенностью, а в окружении вложенность кодируется разделителем, найди каким)
- Почему User Secrets из Этапа 5 внутри контейнера не работают и что используется вместо них

Проверь экспериментально: передай строку подключения только через окружение контейнера и убедись, что она перекрыла значение из `appsettings.json`.

## Шаг 5. Хранение данных

Задача: с SQLite в контейнере есть ловушка. Файл базы данных лежит внутри файловой системы контейнера, а она исчезает вместе с контейнером. Проверь на практике: создай заказ, удали контейнер, запусти новый и посмотри, на месте ли данные.

Затем реши проблему через **том**: смонтируй каталог так, чтобы файл `.db` жил вне контейнера. Здесь пригодится ответ на вопрос про пользователя из шага 3 (у него должны быть права писать в смонтированный каталог).

Вопрос для самостоятельного решения: стоит ли в контейнере остаться на SQLite или это точка, где разумно перейти на PostgreSQL в отдельном контейнере? Выбор за тобой, но сформулируй, чем он обоснован.

## Шаг 6. Миграции в контейнере

Задача: подумай, **когда** и **кем** должны применяться миграции в контейнерной среде. Варианты, которые стоит сравнить:

- Применять при старте приложения
- Отдельным шагом до запуска сервиса
- Вручную

У каждого есть цена (гонки при нескольких репликах, права доступа, время старта). Выбери подход для учебного сервиса и запиши обоснование.

## Шаг 7. docker-compose

Задача: опиши запуск сервиса (и базы, если вынесешь её в отдельный контейнер) в одном файле compose. Задай в нём порты, переменные окружения, тома и порядок запуска.

Разберись и подключи health check из Этапа 7: как Docker узнаёт, что контейнер здоров, и почему в образе `aspnet` для этого нельзя просто вызвать `curl` (проверь, есть ли он там вообще, и как это обходят).

## Шаг 8. Проверка понимания

1. Почему финальный образ собирают отдельной стадией без SDK?
2. Что случится с данными SQLite при удалении контейнера и как это предотвращает том?
3. Почему конфигурацию передают через окружение контейнера, а не вшивают в образ?
4. Чем readiness отличается от liveness в контексте Docker и оркестраторов?

## Критерий закрытия этапа

- Есть рабочий `Dockerfile` с многостадийной сборкой и `.dockerignore`
- Контейнер запускается, API отвечает, настройки приходят из окружения
- Данные переживают удаление и пересоздание контейнера
- Сервис и его зависимости поднимаются одной командой через compose
- Health check учитывается Docker'ом
- Понятны ответы на 4 контрольных вопроса

## Что остаётся за границей этапа

Публикация образа в registry, CI/CD (GitHub Actions), Kubernetes, оркестрация и масштабирование, управление секретами уровня продакшена (Vault и подобные): всё это уровень 2.
