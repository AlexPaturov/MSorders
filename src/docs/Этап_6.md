# Этап 6. Валидация и обработка ошибок

## Зачем этот этап

Сейчас сервис доверяет входным данным: если прислать невалидный запрос, скорее всего, будет либо падение с трассировкой стека, либо тихая порча данных. Реальный API должен явно и предсказуемо отвечать на плохой ввод.

## Шаг 1. Валидация модели запроса

Задача: отдели модель, которая приходит с клиента (так называемый DTO — Data Transfer Object), от модели `Order`, которая хранится в БД. Это важный архитектурный момент: клиент не должен присылать (и получать) ровно то же, что лежит в базе — например, id при создании задаёт сервер, а не клиент.

На DTO для создания/обновления повесь атрибуты валидации (`[Required]`, `[Range]`, `[MaxLength]` и т.п. — разберись, какие подходят под твои поля). `[ApiController]`, который ты уже использовал, автоматически проверяет `ModelState` и возвращает `400`, если валидация не прошла — но сам разберись, как это проверить на практике и что именно вернётся клиенту в теле ответа.

## Шаг 2. Разделить "не нашли" и "сломалось"

У тебя уже есть сценарий 404 (не нашли по id) из Этапа 3. Теперь добавь различение:

- **400** — клиент прислал плохие данные (провалилась валидация)
- **404** — ресурс не существует
- **409** — конфликт (например, пытаются создать то, что уже есть, если у тебя в модели появится уникальность)
- **500** — непредвиденный сбой на стороне сервера (не вина клиента)

Задача-вопрос: для какого из CRUD-методов, которые ты уже написал, сейчас отсутствует нормальная обработка хотя бы одного из этих случаев? Пройдись по каждому методу осознанно.

## Шаг 3. Глобальная обработка исключений

Задача: вместо `try/catch` в каждом методе контроллера — разберись с единым механизмом обработки необработанных исключений на уровне всего приложения. В .NET 8 для этого есть специальный интерфейс (`IExceptionHandler`) — разберись, как он регистрируется и как использовать его вместо обёртывания каждого метода контроллера в try/catch.

Смысл: бизнес-ошибки (не нашли, невалидно) — это нормальный поток, их обрабатываешь сам через статус-коды. А вот неожиданный сбой (упала БД, NullReferenceException по недосмотру) — должен попадать в общий обработчик, который не покажет клиенту внутренности стека, а вернёт аккуратный `500`.

## Шаг 4. Единый формат ошибки

Задача: разберись со стандартом **ProblemDetails** (RFC 7807) — это уже встроенный в ASP.NET Core формат ответа об ошибке (поля вроде `title`, `status`, `detail`). Убедись, что и ошибки валидации, и твой глобальный обработчик исключений возвращают ответ в едином формате — клиенту не должно быть сюрпризом, что 400 выглядит иначе, чем 500.

## Шаг 5. Проверка через Swagger

Пройдись по сценариям руками:

- Отправь запрос на создание с пустым обязательным полем → ожидай 400 с понятным телом ответа
- Запроси несуществующий id → 404
- Намеренно вызови внутреннюю ошибку (например, временно закомментируй проверку на null) → убедись, что клиент видит аккуратный 500 с ProblemDetails, а не стек-трейс

## Шаг 6. Проверка понимания

1. Почему DTO для создания/обновления не должен быть тем же классом, что `Order` в БД?
2. В чём разница между ошибкой, которую ты обрабатываешь сам (404, 400), и той, что улетает в глобальный `IExceptionHandler`?
3. Зачем нужен единый формат ошибки (ProblemDetails), если можно просто возвращать текст?

## Критерий закрытия этапа

- Есть отдельные DTO для входных данных с валидацией
- Методы возвращают осмысленные статус-коды для всех разумных случаев (400/404/409 где применимо)
- Есть глобальный обработчик необработанных исключений
- Ошибки выглядят единообразно (ProblemDetails)
