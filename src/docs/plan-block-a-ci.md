# Блок A. CI: автоматическая сборка, тесты и сборка образа

План действий для блока A из `plan-level-2.md`.

## Цель блока

Push в ветку запускает сборку и тесты, красный тест блокирует слияние, Docker-образ собирается в CI. Деплой и публикация образа в registry в блок не входят.

## Текущее состояние (проверено в репозитории)

1. Решение `Orders.sln` лежит в корне, в нём два проекта: `src/Orders.csproj` (net8.0, Web) и `tests/Orders.Tests/Orders.Tests.csproj` (xUnit).
2. Папки `.github` нет, CI не настроен.
3. Dockerfile находится в `src/Dockerfile` и рассчитан на контекст сборки `src`: он копирует `Orders.csproj` относительно себя. Образ слушает порт 8080.
4. Тесты используют `Testcontainers.PostgreSql`, поэтому на раннере CI должен быть доступен Docker.
5. Git remote `origin` существует: `github.com/AlexPaturov/MSorders.git`.
6. `Program.cs` при старте выполняет `db.Database.Migrate()`, поэтому для тестов поднимается реальный Postgres-контейнер.
7. Тесты проходят локально: 20 из 20.

## Последовательность действий

1. Зафиксировать «зелёную» локальную базу.
   1.1. Проверить, что установлен .NET 8 SDK.
   1.2. Проверить, что запущен Docker (из-за Testcontainers).
   1.3. Выполнить локально restore, build в Release и test в Release. Это эталон, который CI должен воспроизвести.

2. Подготовить репозиторий на GitHub.
   2.1. Убедиться, что `master` запушен в `origin` и на GitHub виден актуальный код.
   2.2. Выбрать события CI: push в `master` и pull request в `master` (для блокировки слияния нужен PR-триггер).

3. Создать файл workflow.
   3.1. Создать в корне репозитория папку `.github/workflows/`.
   3.2. Создать в ней файл, например `ci.yml`.
   3.3. Описать в нём имя workflow, триггеры (`push`, `pull_request`) и одну или две job.

4. Собрать job «сборка и тесты».
   4.1. Указать `runs-on: ubuntu-latest` (там есть предустановленный Docker).
   4.2. Добавить шаг checkout репозитория.
   4.3. Добавить установку .NET SDK 8.0.x.
   4.4. Добавить шаг restore решения `Orders.sln`.
   4.5. Добавить шаг build в конфигурации Release.
   4.6. Добавить шаг test в конфигурации Release.
   4.7. Добавить кэширование NuGet-пакетов, ключ кэша привязать к `*.csproj` или `packages.lock.json`.

5. Собрать job «Docker-образ».
   5.1. Сделать её зависимой от job сборки и тестов, чтобы образ собирался только после зелёных тестов.
   5.2. Собирать образ с контекстом `src` и Dockerfile `src/Dockerfile` (не корень репозитория, иначе путь к `Orders.csproj` не совпадёт).
   5.3. Тег образа привязать к SHA коммита или номеру запуска.
   5.4. Публикацию в registry не делать: она вне блока.

6. Настроить блокировку слияния по статусу CI.
   6.1. В настройках GitHub открыть Branches и создать правило защиты для `master`.
   6.2. Включить требование прохождения status check от нового workflow.
   6.3. Убедиться, что слияние PR без зелёного CI недоступно.

7. Проверить, что критерий блока выполнен.
   7.1. Сделать обычный push и увидеть, что workflow запустился и прошёл.
   7.2. Специально сломать один тест, запушить в ветку и открыть PR: увидеть красный статус и невозможность слияния.
   7.3. Вернуть тест в рабочее состояние и убедиться, что PR снова зелёный.
   7.4. Открыть лог job сборки Docker и убедиться, что образ собрался.

## Частые грабли этого проекта

1. Контекст Docker равен `src`, а не корню: иначе `COPY Orders.csproj` не найдёт файл.
2. `Testcontainers` требует Docker на раннере. `ubuntu-latest` подходит, Windows-раннер потребует отдельной настройки.
3. `dotnet test` ищет тестовый проект через решение. Без `Orders.sln` можно захватить не тот проект.
4. Кэш NuGet ключуется по csproj-файлам, иначе он либо всегда промахивается, либо отдаёт устаревшие зависимости.
5. Тесты поднимают Postgres-контейнер, поэтому первый запуск в CI заметно дольше локального.
