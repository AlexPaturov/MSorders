Этап 4. Реальная база данных (EF Core)

Зачем этот этап

До сих пор данные жили в памяти и пропадали при перезапуске сервиса. Настоящий микросервис хранит состояние в базе. Задача этапа — заменить in-memory хранилище на EF Core, не меняя контроллеры (если Этап 3 сделан правильно с DI, контроллеры вообще не должны почувствовать разницу).

Шаг 0. Выбор СУБД

Реши сам: SQLite (файл на диске, ноль инфраструктуры, идеально для обучения) или сразу PostgreSQL (ближе к реальному продакшену, но потребует локально поднятый сервер или Docker — который у нас всё равно будет на Этапе 9).

Если сомневаешься — начни с SQLite: цель этапа — понять EF Core, а не администрирование БД. На Postgres переключишься позже почти без боли, если правильно спроектируешь слой доступа к данным.

Шаг 1. Пакеты

Задача: разберись, какие NuGet-пакеты нужны для EF Core с выбранной СУБД (провайдер под SQLite/Postgres отличается) и какой понадобится для миграций из командной строки. Найди их самостоятельно через dotnet add package — заодно попрактикуешься читать, что вообще ставится в проект.

Шаг 2. DbContext

Задача: создай класс, наследующий DbContext. В нём должен быть DbSet<Order>.

Вопрос для самопроверки: DbContext регистрируется в builder.Services — с каким временем жизни (Singleton/Scoped/Transient) это принято делать и почему именно так? (подсказка: подумай про параллельные запросы и про то, что EF Core объекты не потокобезопасны)

Шаг 3. Строка подключения

Задача: строка подключения к БД не должна быть захардкожена в коде — вспомни Этап 5 из общего плана (конфигурация), но по факту тебе придётся частично забежать туда уже сейчас: положи строку подключения в appsettings.json и прочитай её через IConfiguration при регистрации DbContext.

Шаг 4. Первая миграция

Задача: разберись с командами EF Core CLI для создания и применения миграции (dotnet ef migrations add ..., dotnet ef database update). Если команда dotnet ef не находится — разберись, почему (нужен отдельный инструмент, ставится отдельно от пакетов проекта).

После этого шага должен появиться файл базы данных (для SQLite) или таблица в Postgres — проверь это глазами, а не только по отсутствию ошибок в консоли.

Шаг 5. Замена хранилища

Задача: перепиши сервис-хранилище из Этапа 3 так, чтобы он работал через DbContext вместо списка в памяти. Реализация методов интерфейса (тот же контракт: Order?, bool и т.д. — см. предыдущее обсуждение) должна остаться прежней снаружи.

Ключевой момент для самостоятельного разбора: EF Core — это не просто "тот же список, но в файле". Есть понятие отслеживания изменений (change tracking) и вызов SaveChangesAsync() — без него ничего не сохранится. Разберись, в какой момент CRUD-методов его нужно вызывать и почему Add/Remove на DbSet сами по себе ничего не пишут в базу.

Отдельно подумай про асинхронность: методы EF Core в основном имеют Async-версии (ToListAsync, FindAsync, SaveChangesAsync). Стоит ли переписать весь путь (контроллер → сервис → хранилище) на async/await, или можно оставить синхронным — и почему один вариант лучше другого для веб-сервиса.

Шаг 6. Проверка через Swagger

Пройди тот же сценарий, что и в Этапе 3 (создать → получить список → обновить → получить → удалить → получить), но теперь дополнительно: перезапусти сервис между шагами и убедись, что данные пережили перезапуск. Это и есть доказательство, что база реально работает, а не просто не падает.

Шаг 7. Проверка понимания

  1. Что произойдёт, если вызвать _dbSet.Remove(order) и не вызвать SaveChangesAsync()?
  2. Почему DbContext обычно регистрируют как Scoped, а не Singleton?
  3. Чем отличается миграция от простого EnsureCreated() — и почему в реальном проекте используют именно миграции?

Критерий закрытия этапа

  • Есть DbContext с DbSet<Order>, зарегистрированный через DI
  • Строка подключения — в конфигурации, не в коде
  • Есть хотя бы одна применённая миграция
  • CRUD работает через реальную БД, данные переживают перезапуск сервиса
  • Понятны ответы на все 3 контрольных вопроса
