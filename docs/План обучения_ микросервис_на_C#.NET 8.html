План обучения: свой первый микросервис на C# .NET 8

Цель

Понять, как устроен микросервис, и своими руками собрать один рабочий сервис — от пустого проекта до контейнера, который можно запустить и вызвать по HTTP.

Граница (чтобы не расползтись)

Делаем один сервис — условно назовём его Orders (заказы). На нём проходим весь путь: от «Hello World» API до Docker-контейнера с базой данных.

Входит в план:

  • Структура проекта ASP.NET Core Web API
  • Модель данных, CRUD через REST
  • Работа с базой данных (EF Core)
  • Конфигурация, логирование, обработка ошибок
  • Health checks, Swagger
  • Docker
  • Базовое тестирование

Не входит (осознанно откладываем на «уровень 2», после того как этот план закрыт):

  • Общение нескольких микросервисов между собой (HTTP-клиенты, gRPC)
  • Message brokers — RabbitMQ, Kafka, event-driven архитектура
  • Kubernetes, service mesh, оркестрация
  • CQRS, Event Sourcing, DDD-тактика (агрегаты, value objects и т.д.)
  • Аутентификация/авторизация (JWT, OAuth) — можно добавить отдельным блоком по желанию
  • Distributed tracing (OpenTelemetry и т.п.)

Если в процессе захочется куда-то из этого свернуть — я буду останавливать и предлагать зафиксировать это как отдельный следующий план, а не смешивать с текущим.

Формат работы

  • Я объясняю что и зачем, ты пишешь код сам.
  • Идём по шагам: от простого к сложному, каждый шаг даёт что-то рабочее и проверяемое.
  • Код и структуры я показываю только как ТЗ/схему в артефактах — не пишу готовые решения за тебя.

Этапы

Этап 0. Подготовка окружения

Зачем: убедиться, что инструменты стоят и работают, прежде чем писать первую строчку. Что: проверка .NET SDK, выбор IDE (Rider/VS/VS Code), первый dotnet --version.

Этап 1. Скелет проекта

Зачем: понять, из чего вообще состоит Web API проект — что такое Program.cs, минимальный хостинг, что происходит при dotnet run. Что: создание пустого Web API проекта, разбор что уже сгенерировано, первый запуск, первый ответ от сервиса.

Этап 2. Простейший endpoint

Зачем: понять маршрутизацию (routing) и разницу между Minimal API и контроллерами — это архитектурное решение, которое ты примешь сам. Что: один GET-эндпоинт, который отдаёт статичные данные.

Этап 3. Модель данных + CRUD в памяти

Зачем: понять, как выглядит доменная модель сервиса и базовые REST-операции, ещё без базы данных — чтобы не мешать две сложности сразу. Что: сущность Order, эндпоинты Create/Read/Update/Delete, хранение в памяти (список/словарь).

Этап 4. Реальная база данных (EF Core)

Зачем: научиться подключать persistence — это то, без чего сервис не «настоящий». Что: выбор БД (SQLite для простоты или Postgres), EF Core, миграции, замена in-memory хранилища на БД.

Этап 5. Конфигурация и окружения

Зачем: сервис должен вести себя по-разному в dev/prod, секреты не должны жить в коде. Что: appsettings.json, appsettings.Development.json, переменные окружения, IConfiguration.

Этап 6. Валидация и обработка ошибок

Зачем: реальный API должен нормально отвечать на плохие запросы, а не падать с трассировкой стека. Что: валидация входных данных, единая обработка исключений (middleware), правильные HTTP-статусы.

Этап 7. Логирование и health checks

Зачем: понять, как сервис «наблюдается» — базовая обсервабилити, без которой в проде нельзя. Что: ILogger, структурированные логи, /health эндпоинт.

Этап 8. Swagger / OpenAPI

Зачем: у любого API должна быть самодокументируемая спецификация. Что: подключение Swashbuckle, разбор сгенерированной документации.

Этап 9. Docker

Зачем: микросервис почти по определению живёт в контейнере — это финальный шаг «упаковки». Что: Dockerfile, сборка образа, запуск контейнера, при желании docker-compose с БД рядом.

Этап 10. Тестирование

Зачем: закрепить уверенность, что сервис работает, и научиться менять код без страха. Что: unit-тесты бизнес-логики, интеграционные тесты через WebApplicationFactory.

Как проверяем, что этап закрыт

На каждом этапе — конкретный работающий результат (запускается, вызывается, видно поведение), а не просто «прочитал». Переходим дальше только когда предыдущее реально работает у тебя руками.

Дальше (уровень 2, отдельным планом)

Аутентификация, взаимодействие сервисов, брокеры сообщений, Kubernetes — когда этот план будет закрыт.
