Этап 5. Конфигурация и окружения

Зачем этот этап

На Этапе 4 ты уже частично коснулся конфигурации, вынеся строку подключения в appsettings.json. Сейчас цель — довести это до полноценной картины: сервис должен вести себя по-разному в разработке и в проде, а секреты не должны попадать в git.

Шаг 1. Разобраться с иерархией конфигурации

Задача: пойми, откуда ASP.NET Core вообще берёт настройки и в каком порядке они перекрывают друг друга. Источников несколько, и они применяются по приоритету — последний побеждает:

  1. appsettings.json
  2. appsettings.{Environment}.json (например, appsettings.Development.json)
  3. Переменные окружения
  4. Аргументы командной строки

Задача-вопрос: если одно и то же значение задано и в appsettings.json, и в переменной окружения — какое победит? Проверь это не по памяти, а экспериментально: измени значение через переменную окружения и убедись, что оно перекрыло файл.

Шаг 2. Понять, что такое Environment

Задача: разберись, откуда берётся значение ASPNETCORE_ENVIRONMENT и как оно связано с тем, какой appsettings.{Environment}.json подхватится. Посмотри в launchSettings.json — там оно уже задано для локального запуска.

Проверь на практике: смени ASPNETCORE_ENVIRONMENT на Production (через переменную окружения при запуске, не трогая launchSettings.json) и убедись, что поведение сервиса поменялось — например, Swagger в проде обычно по умолчанию не должен быть доступен (это уже стоит в шаблоне — найди, где это настроено, в Program.cs).

Шаг 3. Строго типизированная конфигурация

Пока ты читал строку подключения примерно так — доставал значение по строковому ключу из IConfiguration напрямую. Это работает, но не масштабируется и не даёт проверки типов.

Задача: заведи класс-настройки (Options pattern) для какого-то раздела конфигурации (можно на примере тех же настроек БД или добавь что-то новое, например настройки пагинации). Разберись:

  • Как биндится секция appsettings.json на C#-класс
  • Как этот класс потом внедряется в сервисы через DI (через IOptions<T>)

Шаг 4. Секреты — не в git

Задача: пойми, почему пароль от базы или API-ключ не должны лежать в appsettings.json, который коммитится в git. Разберись с одним из механизмов:

  • User Secrets (dotnet user-secrets) — для локальной разработки
  • Переменные окружения — для прода / контейнеров (пригодится на Этапе 9 с Docker)

Задача на практике: перенеси строку подключения (или любой другой чувствительный параметр) из appsettings.json в User Secrets и убедись, что сервис по-прежнему её видит.

Шаг 5. Проверка понимания

  1. В каком порядке применяются источники конфигурации и почему именно в таком?
  2. Зачем нужен Options pattern, если можно просто читать IConfiguration["Key"] напрямую?
  3. Почему секреты в User Secrets не решают проблему для продакшена — что там используется вместо этого?

Критерий закрытия этапа

  • Понятна иерархия источников конфигурации, проверено экспериментально
  • Есть хотя бы один класс настроек через Options pattern
  • Чувствительные данные вынесены из appsettings.json (через User Secrets или окружение)
  • Понятны ответы на 3 контрольных вопроса

Дальше — Этап 6: валидация входных данных и единая обработка ошибок — сервис должен адекватно отвечать на плохие запросы, а не падать со стек-трейсом.
